How contextual logic works
📌 Same builder, different fields
Organizer selects post type first. The form morphs — only relevant fields appear. No unused inputs, no confusion. Each type has its own card design in the student feed.
🎯 Audience targeting
Every post can be targeted: all students, specific departments, specific academic year, or students who attended a past event. Untargeted students simply don't see the post.
🤖 ML context signal
Post type is a feature signal in the recommendation engine. A student who ignores recruitment posts gets them ranked lower. A student who RSVPs often sees more event posts.
✅ Admin approval gate
All event and recruitment posts go into a "Pending" state. Admin approves before it reaches students. Announcements and gallery posts from verified clubs can auto-publish.

4
Intelligence layer — AI feed, chatbot, analytics
Weeks 12–14
Interaction logging — Log every student action: view (dwell > 3s), click, RSVP, share, dismiss. Store in interactions table. This is the ML training data.
Two-stage recommender — FAISS candidate recall → XGBoost re-ranker. Cache results per user in Redis (10 min TTL). Replace chronological feed with personalised feed.
Semantic cold-start — Sentence-Transformers embeds post tags + student interest tags. New students and new posts matched semantically from day one, before any interaction history.
AI chatbot (RAG) — LlamaIndex indexes all live posts, venues, and FAQs into PostgreSQL vector store. Ollama (Llama 3.1 8B) or Claude API answers student questions contextually.
Organizer analytics — Post-level: views, RSVP rate, attendance conversion, demographic breakdown, feedback ratings, comparison to club average
Gamification — Attendance streaks, badge unlock system, department leaderboard. Admin configures rules; students see progress on their profile.

Why Firebase for auth
🔥 Zero auth infrastructure
Firebase handles password hashing, session tokens, 2FA, OAuth flows, and account recovery. You write zero auth code — just call signInWithPopup and you're done.
📱 Google SSO out of the box
Students use their university Google account. One tap, no new password to remember. Works with Google Workspace EDU accounts natively.
🔒 Firestore security rules
Store role (student / organizer / admin) in a Firestore users doc. Rules enforce: organizers can only write their own posts, students can only read approved posts.
📲 Firebase Cloud Messaging
Free push notifications to web (PWA) and native mobile. Sends "Event starting in 1 hour" and "Your certificate is ready" alerts without a separate notification service.

What stays outside Firebase
All application data (posts, RSVPs, users, interactions, analytics) lives in PostgreSQL — not Firestore. Firebase is used only for authentication and push notifications. This keeps data portable, queryable with SQL, and avoids Firestore read/write costs at scale. The Node.js API uses the Firebase Admin SDK to verify ID tokens on every request.
